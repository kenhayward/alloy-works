## Requirements that need sharpening

- LOC-001 – "none may be assembled from fragments at run time" as written forbids the solution: CLDR plural/gender message forms are assembled with a number, and that is their job. The intent (no grammatical composition in code) is correct; the wording should name the permitted mechanism (ICU MessageFormat / locale-aware categories) or say "assembled by application code rather than locale-aware formatting".
- LOC-002 – whose locale? Per LOC-005 the interface language and content language are independent, so an Arabic UI rendering dates from English content needs a stated rule. Currency has the same problem: tenant default, user setting, or content-intrinsic — one sentence resolves both.
- LOC-006 – "substantially longer" is not verifiable. It needs either an expansion factor as the acceptance bar (German ~35%, Turkish more; 40–50% is a defensible line) or a named test suite, otherwise any amount of stretch can be declared acceptable.
- LOC-013 / status vocabulary – the document requires variants to "carry a status" but never names the state set (draft, machine-translated, approved, out-of-date). GEN-022's terms cover the MT marking only; nothing covers retranslation states. Define them here or cite where the state machine lives — currently it is neither.
- LOC-014 + LOC-015 + LOC-017 taken together – "a typo fix is not a new translation job" requires classifying every source edit as semantic versus editorial, immediately (014), with publish refusal riding on the result (017). If that classification is manual, each small source edit either blocks publishing of every dependent translation or costs human triage. State who or what performs the classification, or relax "immediately" to "at the next status recomputation".
- LOC-022 – the trackable list omits which version of the source was sent. That datum is required to answer the in-flight conflict below; it costs nothing to add now.
- Language versus locale – Depends-on cites CNT-083/084 as "language is recorded". LOC-002 and LOC-003 are only implementable if that tag is a BCP 47 locale (pt-BR distinct from pt), not an ISO 639-1 code. Worth one confirming sentence, or regional variants silently cannot be implemented downstream.
  Missing areas
- In-flight round-trip conflict – the largest gap: the source changes while a vendor job is out; the import arrives against a stale base. LOC-021 covers placement failure (nothing dropped without being reported), not version conflict — accept as fresh retranslation, reject, or mark for review? No requirement owns what happens on the return leg, even though it follows directly from LOC-008 and LOC-013.
- Dangling policy objects – "a declared policy" (LOC-011), "by policy" (LOC-017) and tenant policy (LOC-026) appear with no requirement or Depends-on entry locating where policies are defined. Related: fallback-to-source at component granularity can yield a page that is nine-tenths translated, which sits uncomfortably against N04's "no mixed-language output by accident". State whether the fallback in LOC-011 is per-component or document-level — as written both readings are permitted and they contradict each other in spirit.
- Supported language/locale set – nowhere states what must be supported at launch, and who supplies locale data (CLDR) for dates and collation; LOC-002/003 silently depend on it. If another document owns that, add it to Depends-on; if none does, the gap is real.
- Content-side grammar – section 4 covers variants and status but says nothing about locale-aware formatting inside variant text (plural forms for numbers in content, not just interface strings). This may legitimately belong to CNT — a cross-reference or one line prevents it being silently unowned by both documents.
- Retranslation assist tension – N02 pushes translation memory to the vendor while LOC-015 makes retranslation a first-class workflow. With no TM and machine translation as the only assist (LOC-023), post-change retranslation starts from nothing or from raw MT output. If that is deliberate, one acknowledging line stops reviewers asking whether it was missed.
- Acceptance mechanics for machine drafts – LOC-024 defers to GEN-022 "on the same terms"; verify that GEN-022 defines the act of acceptance (who may flip a draft variant to approved), not merely the marking. IAM owns "who may translate", so the accepting role has to sit somewhere explicit.
- Testability hooks – pseudolocalisation strings, RTL smoke tests: none appear anywhere in the document. If the set carries an acceptance-criteria or test document this belongs there; if it does not, LOC-004 and LOC-006 are stated but unverifiable in practice.

## One internal tension to close before review ends

- LOC-Q03 against LOC-020. Constraint 020 says bindings "must not be translatable as text"; question Q03 asks whether bound values (category names returned by a query) get translated, and its own settlement note concedes that display text is usually what sources hold. If the answer lands on "yes", it needs a render-time mechanism (translate resolved values against a lookup, keep bindings inert in the variant), and the document should say so — otherwise a constraint and an open question in the same section read as contradicting each other.
