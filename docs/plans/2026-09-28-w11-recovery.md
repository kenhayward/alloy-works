# W11: Recovery

> **A sketch**, built a pull request at a time, each test-first with one final whole-branch review
> before it opens that is asked for a break of its own against every citation. It builds W11 of
> [the rest of T1](2026-09-25-t1-remainder.md) from component-editor.md's
> [Recovery, as W11 builds it](../design/component-editor.md#recovery-as-w11-builds-it) and
> storage-and-versioning.md's VER-003 and VER-004, whose decisions RC-A to RC-H were taken as
> recommended on Ken's instruction of 2026-09-28 to continue, and are his to review.

**Goal:** nothing an author saw saved is lost to a closed tab, a reload or a crash; they can see and
restore what they saved; undo survives a reload; and iterations are kept exactly as long as the tenant
says after the next cut, then swept.

## Global constraints

- Test titles cite only what they show, checked with `pnpm trace show <ID>`, in a literal title.
- Each test is watched fail: a new test before the code, or, where the code exists, by breaking it.
- No em or en dash in user-facing text, and no real names, addresses or paths in a fixture.
- `pnpm typecheck`, `pnpm lint`, `pnpm format`, the affected suites, then `pnpm trace generate` after
  Prettier and `pnpm trace pins`; the full suite before each pull request, and its CI log read.
- Iterations stay immutable (VER-001): nothing in W11 updates a row, and the only delete is the sweep's.
- A migration is checked against every write path the stored shape admits.

## W11.1: Retention

1. Migration: a singleton `editing_policy` with `iteration_retention_days` (30; 1 to 365); `expires_at`
   dropped from `iteration`; an index for the sweep; the runtime role granted `delete` on `iteration`
   behind a trigger that refuses any row whose opened-from version has no successor cut more than the
   window ago.
2. `GET` and `PUT /v1/settings/editing`, `administer` on the tenant.
3. The worker's interval sweep removes iterations past their window in every tenant.
4. Tests: VER-003 (kept while no later version exists however old; kept for the window after the next
   cut; swept after it; the trigger refuses an early delete), VER-004 (the default stated and read; set by
   an administrator, refused to anyone else; the sweep follows a changed window).

**W11.1, as built.** Migration 0037 makes `editing_policy` one row, as `access_policy` is, its
`iteration_retention_days` 30 by default and checked from 1 to 365; the runtime role reads it and may
update that column alone. `iteration.expires_at` and its check are gone, and nothing read them but the
insert and the VER-001 test, which now says the runtime role cannot change an iteration nor remove one
before its window. `ITERATION_RETENTION_DAYS` stays as the default's constant, which a test holds to the
column's default. The runtime role may delete an iteration behind `iteration_swept_only`, which finds the
next cut as the first version after the opened-from one by `(revision_no, version_no)` and refuses the
delete unless that version's `created_at` and the window are at or before `now()`; `artifact_version`
has no trigger, so the tests move a cut back as the administrator. `sweepIterations` deletes by the same
condition, and `iterationRetained` states it as a SQL expression over an alias, for W11.2's listing. The
two routes are `GET /v1/settings/editing`, to any session, since a window only an administrator could
read would not be stated, and `PUT`, `administer` at the tenant, whose out-of-range body the contract's
schema answers `400 invalid_request` before the handler; `setEditingPolicy` refuses the same range as
`retention.out_of_range`, and the handler answers that as the same `400`. The access and cross-tenant
harnesses each needed the `PUT`'s entry. The worker's `sweepExpiredIterations` runs on the sign-in
sweep's interval; its test breaks one tenant by revoking its delete grant.
**From the final review:** the delete guard read `artifact_version` and `editing_policy` by the search
path, where a session's temporary tables come first, so the runtime role could shadow either and delete
an iteration nothing had been cut after; it now reads both by its own schema, as the publishing triggers
do, and a test shadows both and is refused. The however-old refusal is now shown with the version it was
opened from long past too, and the window's change is refused to somebody who authors across the whole
environment, not only to a space's administrator.

## W11.2: Recovery

1. `GET /v1/components/{id}/iterations` (a cursor, newest first, no content) and
   `GET /v1/components/{id}/iterations/{iteration}`, both for the caller's own rows while they hold the
   lock, and only rows the sweep would keep.
2. The component's `GET` answers its caller the time of their newest iteration opened from the latest
   version (RC-F).
3. The editor: **Recover** offered above the text; a Recovery state and panel listing the iterations,
   restoring one after flushing the current state as an iteration; history and stored steps cleared.
4. Tests: CNT-174 (the writer reads under the lock; another holder, a reader and the writer without the
   lock are refused), CNT-090 (listed newest first and restored, content and values), CNT-067 (after a
   closed tab, what was saved is offered and restored).

**W11.2, as built.** `packages/db/src/recovery.ts` holds the three reads. `listIterations` pages a
principal's own iterations of one component through the listings' `keysetPage`, over a new `iterations`
listing sorted by `created_at` descending and then the id, joined to the version each was opened from
for its number, and filtered by `iterationRetained`, so it answers exactly what the sweep keeps; it
takes a snapshot for the cursor's shape but filters nothing by it, as `listPeople` does not, since an
iteration is never changed, only swept. `readIteration` answers one whole under the same filter, and
nothing alike for another principal's, another component's, a swept one or an id that is not one.
`newestUncutIteration` answers the `created_at` of the principal's newest iteration opened from the
latest version, and **null where that iteration's digest is the latest version's content and values**,
a refinement of RC-F: text changed and changed back, then released with nothing to cut, would otherwise
be offered as unsaved work every time the component opened. The two routes are
`GET /v1/components/{id}/iterations` and `GET /v1/components/{id}/iterations/{iteration}`, `edit` on the
component, and **each names the asking session in a `session` query**, as `DELETE .../lock` does, since
`holding` needs the session and the design's table named no way to carry it; a session that does not hold
the lock is refused through the same mapping as a save, `lock_held` or `lock_required`, and any iteration
id not the caller's own is a 404. The listing uses `pageAsked` and `cursorFor`, and API-007's walk over
every listing includes it, over two iterations the test saves. `GET /v1/components/{id}` gains `unsaved`,
`{ savedAt }` or null, and creating answers null. The access and cross-tenant harnesses each needed both
routes. In the renderer, the session has a seventh phase, `recovery`, which the surface does not take
changes in: `recover()` claims **always afresh and always with `move`**, from reading or from a
`recoverable` lost - afresh because the id a reload keeps may already have saves past this page's
count, which the first save after a restore would then find stale; with `move` because the author asked
to recover here, and a lock another author holds refuses it all the same, naming them. A claim into
Recovery with unsent changes schedules their save at once, so what was on screen is usually saved
before the author chooses; `restore` forces the flush again and waits for it, then reads, then calls the
component's `open`, which runs `readContent` - the migration chain and the parse, CNT-012 and CNT-013 -
and `toEditor`, refuses by the iteration's time what will not read or will not edit, and otherwise puts
the text in a fresh state, so the history goes with it, and the values in the fields; the restored text is
then sent at once. The adapter answers each listed row as this window's where its session is the one the
adapter holds now. `RecoveryPanel` is a region in the `F6` ring, focused as it opens, closed by `Escape`
or **Close**, with **Restore** named by the time to the second and **Show older** moving the focus to the
first row it adds; the focus goes back to the text as it closes. The notice above the text is a new
`Notice` tone, `unsaved`, with the `--warn` edge. Not built: Recovery in a window that lost the lock to
a move or to another author, and an offer of saves opened from a version older than the latest - both
named in [Two windows, one author](../design/component-editor.md#two-windows-one-author).
**From the final review:** Recovery could be entered only from reading or a stale `lost`, so saves
opened from an older version, work typed before a Recover, and the state flushed before a restore were
never offered; `recover()` now enters it from `editing` too, flushing first and claiming nothing, and
**Saved text** in the strip, disabled except while editing, asks for it. `newestUncutIteration` now answers
the newest retained iteration unless a version at or after the one it was opened from holds its digest,
so work somebody else's cut left out is offered while it is kept, and the author's own cut still offers
nothing; its test cuts from Grace's session and then moves the cut past the window. The notice was
wrong in a second window: where the author's own other window holds the lock it now says they are
editing in another window and offers **Recover here**, and where somebody else holds it offers nothing.
The panel's window column compared a row's session with the adapter's current one, which Recover always
replaces, so the adapter now keeps every session id this window has used for the component in session
storage, `editingSessionFor`'s and each fresh claim's, and marks a row this window's by any of them. A
listing or read refused `lock_required` now claims again once under the same session, as a save does,
instead of a dead end; the panel says what is saved first only where something is unsaved; and the
CNT-090 web test now holds the flushing save open and shows nothing is read until it is answered,
watched red with the flush skipped. The Recovery panel is in the `F6` ring, and a test shows it. The
one gap left is the window that loses the lock to a move.
**From the re-review of those fixes:** a refused claim left the lock unread, so the notices came back -
**Recover** beside Grace's name, and the never-made-a-version sentence beside the author's own other
window; both now follow the holder the refusal named. A refusal that stops the saving no longer lets
**Saved text** open the panel over its reason. And the Saved text test now holds the save open, so it
shows the listing waits for it.

## W11.3: Undo across a reload

1. Session storage per component: the opened-from version and document, the steps with their history
   grouping, the values, the last sequence sent.
2. The component's `GET` answers the caller's own session its latest accepted sequence.
3. On reload: claimed again under the same session where nobody else holds the lock, the steps replayed,
   anything past the service's sequence sent; another holder means Reading with the changes offered as
   text; a version cut since discards the steps.
4. The title editor's history without a depth limit.
5. Tests: CNT-069 (undo after a reload reaches back to where the session opened), CNT-067 (a reload
   loses nothing past the last acknowledged save), CNT-169 (steps from before a cut discarded).

**W11.3, as built.** The steps are kept as a log of changes rather than bare steps in groups:
`recordChange` in `packages/editor/src/replay.ts` takes each transaction the surface applies, with every
one the plugins appended, each its steps, whether the history holds it and the selection it set, and
records how the history took it - `new`, `join`, `none`, `undo` or `redo` - off `undoDepth` before and
after. A log, because the identifiers the identity plugin draws are appended outside the history, and
replaying the history's steps alone would draw new ones and change every block the session split; and
because an undo or a redo is part of what the author had, which CNT-069's "undo and redo" asks to survive.
`replayChanges` replays the log in a state holding the history alone, so no plugin appends or draws
anything, forcing each change's grouping - `closeHistory` before a new event, one composition shared
across an event - replaying an undo or a redo as the command and checking it made the steps recorded,
checking the history's depth after each change, closing the history, and reconfiguring onto the
surface's plugins. `apps/web/src/editor/stored-session.ts` keeps the session under
`alloy-works:editing-steps:<componentId>`: the session, the version opened from, the document then, the
log, the values, a revision bumped by every change, and the sequence and revision of the last save sent,
written after every change and never while nothing has changed; a failed write stops keeping and removes
what was kept. The component's `GET` takes an optional `session` query and answers `sequence`, the
caller's own session's latest accepted, read by `latestSequence` as `saveIteration` reads it - a member
beside the lock, since a lapsed lock is answered as none. On opening, a record of the kept session
against the version that opens, with anything changed, is replayed; the session starts from the larger of
the last sequence sent and the service's, and `resume` claims under the same id, neither fresh nor moving,
holding the changes unsent unless the service accepted the last send and nothing changed after it. A
refusal puts the latest version back, offering the changes as text where any were unsent; where the
service has them, Recover reaches them once the holder is gone (merged with W11.2's re-review, which
offers nothing while somebody else holds the component). A cut, a restore, a refused claim and Done editing - whether or not it cut -
reset the record; a session claimed afresh rebinds it, with nothing sent; a page's session heard from
after its page has gone writes nothing. A replay opens with a caret, never a node selected whole, whose
footnote editor or figure panel the page would not draw. The title's field has `history({ depth: Infinity
})`. The renderer's test set-up clears session storage around every test. Not built: nothing is kept for
a section's title across a reload, which is the documents page's, not the component's.

From the final review: six findings, each fixed test first. **D1**, a reload overwrote a newer save made
under the same session, which a duplicated tab does for real: `continuing` answers `ahead` where the
service's sequence is above the last this window sent, and `behind` then opens the page as a stale save
leaves it, sending and claiming nothing; each sequence sent is also kept under
`alloy-works:editing-sent:<componentId>:<session>`, only ever rising and written after the page has gone
too, so a page's own last save is not taken for somebody else's. (A page mark that told a duplicated
tab from a reload was built here too and taken out by the re-review, below.) **D2**: the record carries its principal, and `readKept` gives it
to nobody else; the Header's Sign out forgets every `alloy-works:editing-` key. **D3**: the component's
`GET` names the kept session id whether or not a record is kept, and a page reusing that id starts at the
service's sequence, so a reload straight after Save version or a restore no longer claims "newer text";
the test's fake now reports the lock held by the session that claimed it. **D4**: the record is written at
most 300 ms after a change, at once for a send, a reset and a close, and on `pagehide` and the page
hidden; full storage forgets other components' records before it stops; `mergeChange` keeps a run of
typing as one step. **D5**: the record is stamped with a format and `editorSchemaIdentity`; one of another
format or model, one that will not replay and one the author may no longer edit are offered as text to
copy, from `replayPlain`, where that differs from what opens, and said lost where nothing can be read.
**D6**: the user-facing words say "anything not yet saved". CNT-069's test now types a joined pair - a
word and, a tenth of a second later, the deletion of its last letter, which the history joins and
`Step.merge` cannot - and shows one undo taking both after the reload; for "scoped to the component being
edited" it shows only that another component's kept record is left untouched, not that the history is
the component's alone, which the one-view-per-component design (ADR-0023) gives.

From the re-review of those fixes: six findings, each fixed test first, and one gap named.
**The page mark is gone.** A crash, a discarded tab or a session restore fires no `pagehide`, so the mark
stayed and the next load of the same tab was taken for a duplicate: undo lost, the lock read as another
window's and the unsent text left in a box the next claim cleared. `markPage`, its calls from `main.tsx`
and the component's `GET`, and forgetting copied session ids are removed; a reload after a crash - a
remount with no `pagehide` - replays and goes on, and CNT-069's second test shows it. The sequence rule
stays, and is what protects: a reload never sends where the service holds more under its session than
this page sent (`behind`, over `alloy-works:editing-sent:<componentId>:<session>`). A genuine duplicate
goes on as a second window under the same session, and the service refuses the older sequence of the
two, whose page goes `lost` with its text offered. **Text offered on opening stays until dismissed.** It
is held apart from a refusal's kept text, which a successful claim still clears, in session storage under
`alloy-works:editing-offered:<componentId>` stamped with the principal, so a reload shows it again, and
**Dismiss** forgets it; a replay the service has saved past is offered this way too. **Sign out forgets
everything.** `forgetEditing` runs again just before `onSignedOut`, and sets a flag that
`mayKeepEditing` in `apps/web/src/editor/editing-storage.ts` answers, which every write of a record, a
sent sequence, an offered text and a session id asks first, so nothing is written for the rest of the
page; the flag lives there rather than in `stored-session.ts` so the shell still reaches it without
ProseMirror, and the test set-up clears it before every test. **A session reused with no record** starts
at the larger of the service's sequence and `sentFor` its session. **The model's identity** hashes every
node's and mark's spec, keys sorted, less functions and `parseDOM`, `toDOM` and `leafText`, so `excludes`,
`group`, attribute defaults and flags such as `defining`, `atom` and `code` count. **The merge guards**
each have a test that goes red without them: the recorder's check that a change starts from the selection
the last one left, and `mergeChange`'s refusal where the first sets a selection and the second does not.
**Known gap, not fixed:** a page restored from the back-forward cache, after another page in the same tab
ran the same session, can write its older record over the newer one. The undo the newer page had goes
from the record, but no text is lost: the restored page's next save carries an older sequence, which the
service refuses, and the page goes `lost` with its text offered.

From a second look at those fixes: one defect and three minor points, each fixed test first. **D1**, a
save refused at an equal sequence was later taken as saved: the sent key records a sequence as it is
sent, so a page whose save of n+1 was refused because another page of the same session saved n+1 first,
or whose last save, sent as it went, met the same, resumed after a reload as "Saved" with nothing
offered. The session now tells `onAccepted` and `onSaveRefused` each answer to a save - stale or
conflicting for a refusal - before anything else and even once disposed, the saves sent as the page goes
among them; the recorder keeps the last answer under `alloy-works:editing-acked:<componentId>:<session>`,
only ever rising and written after the page has gone; and `continuing` takes the service to be ahead
where its sequence equals the last sent without an answer accepting it, or where that number was
refused. The worst of it is a false notice of newer text with the text offered, never a loss: a save
that arrived but whose answer was lost with the page is now offered after a reload rather than taken for
saved. The Reload tests' fake answers an equal sequence as `packages/db` does, again where it holds the
same and conflicting where it does not. **M1**: a fresh claim's session id asks `mayKeepEditing` before it
is kept. **M2**: a sign-out with no answer asks `/v1/me`, and where it does not say nobody is signed in the
page stays and keeps again, through `keepEditingAgain`, rather than keeping nothing for the rest of it.
**M3**: text offered on opening is taken from what the page already shows for the component before what
storage holds, so a component opened over again with storage that refused it still offers it.

From a third look: the false notice was common, since in a real browser the save a page sends as it
goes often arrives and its answer finds the page gone. Where the service's sequence equals the last sent
and no answer to it was kept, the reload now sends that save again at the same number after the claim,
rebuilt exactly from the record - which keeps `sentAs`, the changes and values the last save held, in
format 3, with nothing typed after a send merged into it - and the service's repeat rule settles it:
acknowledged, the page goes on as saved and sends what was typed after as the next sequence; refused as
conflicting, or unanswered, it goes behind with the text offered. A save the record cannot rebuild
exactly goes behind as before. The Reload tests' fake now drops an answer to a page that has gone.
