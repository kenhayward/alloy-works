unapproved content, in a pane beside the text, without leaving it.

## Global constraints

- Test titles cite only what they show, checked with `pnpm trace show <ID>`, in a literal title.
- Each test is watched fail: a new test before the code, or, where the code exists, by breaking it.
- No em or en dash in user-facing text, and no real names, addresses or paths in a fixture.
- `pnpm typecheck`, `pnpm lint`, `pnpm format`, the affected suites, then `pnpm trace generate` after
  Prettier and `pnpm trace pins`; the full suite before each pull request, and its CI log read.
- A migration is checked against every write path the stored shape admits, since a request row is
  written by the service and finished by the worker (the stored shape accepts too much otherwise).

## W10.1: A preview made and kept

1. Migration 0035: `publication_request.kind` (`publish`, `preview`), with `pdf` alone for a preview;
   the preview's key, hash, size and expiry, set only in the move to `done` and only on a preview;
   `finish_once` freezing the kind; `publication_recorded_whole` asking a publication of a publish only.
   The default layout's 0.7 at layout schema 6, with `words.preview`.
2. `packages/domain`: layout schema 6's `preview` words, optional before it; `assemble` told
   `status`, setting the preview's notice and sentence, or failing naming them where the layout has none.
3. `packages/db`: `requestPublication` told the kind, enqueuing `preview`; `recordPreview`.
4. `apps/worker`: the `preview` job, the publish handler told the kind.
5. Tests: PUB-005 (the notice on every page and the sentence once in the tagged text, from a stored
   preview); PUB-006 (the same inputs as a publish of that version, and no publication recorded); the
   store's refusals of a preview with a publication, a publish with a preview's PDF, or a preview in Word.

**W10.1, as built.** Migration 0035 gives a request its kind, a publish by the column's default, and a
done preview its PDF's key, hash and size and its expiry, held by four checks and by the finish-once
trigger, which freezes the kind and keeps the key in the tenant's own store as 0017 keeps an output's.
`requestPublication` names the kind only for a preview, so a publish is written as it was before 0035.
A preview asked for in Word is refused by name before anything is recorded; one under a layout that
makes no PDF would be refused by the check a publish meets, which no stored layout reaches, since the
layout's parse requires a PDF page. `recordPreview` answers when the preview expires, an hour after
the database finished it. `assemble` asks the faces for a preview's words where it sets them, in place
of the draft's, and a publish's never; a preview of a request made before layouts has no words either,
and fails `preview_words_missing` as one under a layout stored before schema 6 does. The code is in
the contract's failure list and has words on the document page. `publicationInputs` now reads the
kind, so the theme migration's tests read the theme a request made at 0026 is handed as that function
reads it, rather than through it.

## W10.2: A preview asked for and swept

1. `POST /v1/documents/{id}/previews`, `read` on the document, body `version`; the same answers as a
   publish's, and `format.unsupported` where the layout makes no PDF.
2. `GET /v1/publication-requests/{id}` gains `kind`, and a done preview's `preview`: `view`, `download`
   and `expiresAt` while it lasts.
3. The sweep: a preview request deleted an hour after it finished, its PDF removed unless another row
   names its key; a publish request never, refused by a trigger.
4. Tests: a reader who may not publish asks for one; a stranger is answered `404`; the links go when it
   expires; the sweep keeps a key another row names. The end-to-end check asks for a preview, which is what shows the worker registers the
   `preview` job (W10.1's review).

**W10.2, as built.** `POST /v1/documents/{id}/previews` is decided on `read` and takes the version
alone, so a format in its body is refused by the contract; its handler calls `requestPublication` told
`preview` and `['pdf']`, in the transaction `read` was decided in, and a publish's and a preview's
answers are mapped by one function, `answered`, so a preview is refused in a publish's words. As a
mutating permission-checked route it honours an idempotency key with nothing added. The request's
view carries `kind` and `preview`, the latter signed only for a done preview that has not expired by
the service's clock, named `{id}-preview.pdf` to download, and `503` where there is no store to sign
it; the contract declares that `503` on `GET /v1/publication-requests/{id}`. Migration 0036 grants the
runtime role `delete` on a request and adds `publication_request_swept_only`, refusing any delete but a
preview's an hour after it finished; the cascades from 0017 and 0022 take its occurrences and images.
**One departure from the plan:** the sweep keeps a preview while another preview of its document
version and its second is still queued. The brief's reasoning, that two previews with one key finish
and expire together, does not hold: one can be retried or wait behind other jobs long after the other
expired, and its worker keeps the bytes before recording them, so a sweep in between would remove
them. `sweepPreviews` takes no clock of its own, since the trigger holds every delete to the
database's. The worker's `sweepExpiredPreviews` runs on the sign-in sweep's interval in every tenant
and removes the keys after the commit, logging and passing over a tenant whose sweep or store fails.
The end-to-end check was run against a stack of this branch in a Compose project of its own, and
failed as expected with the `preview` job's registration removed from `main.ts`. **From the final
review:** a preview's request decides `read` on its document again at every answer, so an asker who
loses it is answered `404` at the next request and signed no more links, as a publication is read on its
own grants at every answer; a tenant whose store cannot be reached once its requests are swept has
their keys logged, since nothing names them again; and a queued preview of the same version in another
second is shown not to hold the sweep back. The sweep's clauses for samples and uploads are defensive
and untested: a PDF shares no hash with a PNG, a JPEG or a sample.

## W10.3: A preview shown

1. **Preview** on the document page for anyone who may read it, in both modes, beside **Publish**.
2. The pane beside the text: the PDF in an `iframe` named for the document, the time it was made, a
   link to download it, and a close button; failures in **Publish**'s words; a second preview replaces
   the first.
3. Tests: CNT-150 (asked for from the document page, shown in the pane, an editor open in place kept).
4. PV-H: a preview of a 300-page document timed from the request to the PDF, recorded here.

**W10.3, as built.** `usePreview`, in `apps/web/src/publishing/Preview.tsx`, holds one preview for the
document page, and the page places its three parts: **Preview**, which `Publishing` renders beside
**Publish**, and alone where Publish is not offered, so a reader in Reading asks for one as an author
in Authoring does (PV-B); what is said of it beside the button, in a polite live region with no
`status` role, as Publish's is; and the pane, a region named **Preview** in a column of its own
between the text and the dock. The grid gains that column while a pane is open, so the text narrows in
place and nothing in it remounts, an editor open in it included, which is what CNT-150's test shows;
under 1100px the pane goes below the text, as the dock does. A preview is followed by the follower
Publish now uses too, `useFollowing` in `following.ts`, which took Publish's timers and doubling
unchanged, and is refused in `refusedWords`, Publish's sentences with the act named, so a stale
version says "Reload it and preview it again." and a publish's says what it said. A `404` at the door
now says "This document is no longer open to you." for both, where a publish said it could not be
asked for. The failures are listed by `FailureList`, which Publish's list became, with `failureWords`
and the page's `placeOf`. The pane shows the PDF by the view link it was answered with, since the
browser has read it by the time the link lapses, and **Download the PDF** reads the request again for
a fresh link each time it is pressed; a request that answers no preview, or `404` once swept, is an
expired preview, said in the pane with **Make a new preview**. The time it was made is `expiresAt`
less the hour `recordPreview` gives it, in local time, in a `time` element. **PV-H, measured:** a
document of 50 sections, each placing one component of 130 paragraphs of about 150 characters, set
to 304 pages and 1.5 MB, was previewed three times on one machine - an Intel Core Ultra 7 270K Plus,
24 cores, 64 GB, Windows 11 Home, PostgreSQL and SeaweedFS in Docker 29.6.1, Typst 0.15.1 - through the
worker suite's own harness: `requestPublication` told `preview`, then `processNext` running the
`preview` job to the stored PDF. From the request to the stored PDF took 1.85 s, 1.74 s and 1.61 s,
of which recording the request took 0.11 to 0.25 s and the job 1.49 to 1.72 s. The measurement was a
throwaway test and is not committed, and no test holds the number (PV-H): plain paragraphs are the
cheapest content there is, and a document of tables, figures and equations will take longer.
**From the final review:** **Download** follows its link in a hidden frame, never the page, since a
navigation of the page would have an editor with unsaved text ask whether to leave, and an error the
store answers would leave the application behind; a link that is not `https:` or `http:` is neither
shown nor followed; a download answered after its preview was closed or replaced moves nothing;
closing the pane gives the focus back to **Preview**; and the layout is checked as a column of the grid
of its own, from the stylesheet's rules, since jsdom lays nothing out. A preview still being made when
the pane closes is still shown once made: the author asked for it. **Left for Ken:** at 1440 pixels the
text and the preview share the width evenly, about 383 pixels each, so the text's measure scrolls
sideways while a preview is open; showing the outline as its rail while previewing would give each
about 510, and is his to choose. Neither the viewer nor the download has been checked in the desktop
app.
