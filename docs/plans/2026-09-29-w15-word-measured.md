# W15: Word measured

> **A sketch**, built a pull request at a time, each test-first with one final whole-branch review
> before it opens that is asked for a break of its own against every citation. It is a workstream the
> [remainder plan](2026-09-25-t1-remainder.md) did not have: W13's plan left STY-081 and PUB-023 as "the
> next thing to plan after W13" (its [Left, named](2026-09-28-w13-browser-suite.md#left-named)), and
> W14.3 dropped PUB-092's claim for the same missing measurement. Its decisions, W15-A to W15-M below,
> are to be taken as recommended and are Ken's to review. **W15-D, W15-H, W15-I and W15-K change what
> can be claimed or what the product does, and are the ones to read first.**

**Goal:** Word is held to the PDF as the editor is. Word's own rendering of a publication - its layout
and its page breaks, as Word exports them to PDF - is measured against the PDF of the same content by
the reader and the comparison W13.4 built, over the themes W13.4 measures and more; Word's pagination
is shown keeping what the styles say to keep; a maths character Word's maths face lacks is judged,
not borrowed; and a requirement only a run on a machine with Word can verify has a place in a
baseline that the gate can read.

**What no local run can close.** CI runs Linux and has no Word, so nothing W15 measures binds on a
pull request. STY-081 asks for an automated suite, and it is one, but it runs where Word is: **it binds
once per release, through the baseline's `local-run` row, and before each change to the Word writer,
the theme's projections or the template by the Word check's practice** (W15-E) - never by CI. A
regression merged between two releases without that practice stays unseen until the next release's
run. And a recipient's Word is not the reference machine's: the run measures one version and build of
Word, recorded, never a range.

## Global constraints

- Test titles cite only what they show, checked with `pnpm trace show <ID>`, in a literal title - never
  `it.each` or a built string, which cite nothing.
- A citation needs a design claiming the requirement first: `pnpm trace check` fails otherwise. Each
  slice adds its claims before its tests.
- **A Word-only test cites only what `local-run` verifies** - STY-081, PUB-092, PUB-029 - never a
  requirement CI verifies by another test, since a skipped citation demotes it (docs/testing.md, the
  Word check).
- Each test is watched fail: a new test before the code, or, where the code exists, by breaking it. The
  measurement's bite is shown by a writer change that moves one property half a point and more.
- No em or en dash in user-facing text, and no real names, addresses or paths in a fixture, a record or
  a report - Ada and Grace, as the stand-in's own.
- A publication already recorded publishes the same again: a new template version is added, never an
  old one changed (W15.3).
- `pnpm typecheck`, `pnpm lint`, `pnpm format`, the affected suites, then `pnpm trace generate` after
  Prettier and `pnpm trace pins`; the full suite before each pull request, and its CI log read, the
  browser step's included; **and on Windows with Word, the whole worker suite with
  `ALLOY_WORD_CHECK=1`, its result pasted into the pull request** (W15-E).
- Word is never started in CI and never by a script the suite does not stop; the Word check's script
  already stops only the process it started.

## Pins

Nothing new from npm: `packages/conformance` takes `pdfjs-dist` at the version the lock file already
names for the worker and the browser suite. **Word cannot be pinned** (W15-E): its version and build
are read from COM on each run and recorded. Cambria Math's file version and sha256 are taken by W15.4's
script from the file itself, never written from memory.

## Questions a slice answers before it builds

Only these could change the plan; everything else is built as written.

1. **W15.1: does W13.4's reader read Word's PDF, and what must it learn?** One export of W13.4's
   fixture under the default theme, read: Word's subset fonts and how their programs are named, its
   text operators and how it splits a line into runs, how it paints a fill, a rule and an underline
   (rectangle or stroke), its colour spaces, and its marked content. What the reader must follow is
   added to it, test first against that export kept as a fixture; if Word's PDF needs a second reader,
   the comparison still stays one.
2. **W15.2: how far is Word from the PDF over the eight themes, before any fix?** The first run's
   differences, each sorted by W15-I. If any needs the PDF to move, or the Word-side fixes are more
   than a slice's worth, the numbers go to Ken before W15.3 is built.
3. **W15.4: does Word set the keep specimen's lines on the PDF's 12pt grid**, so the PDF's count of
   fillers brings the same line to the foot of Word's page? If not, each Word case finds its own count
   from a batch of candidates opened in one Word session, and the expected split is asserted on the
   candidate that brings the line there.
4. **W15.4: what does Cambria Math lack?** On the reference machine, how many of the characters the
   maths tree can hold, and of the symbol palette's mathematical group, the installed Cambria Math
   lacks. If it lacks characters an author is likely to type, the refusal's cost comes to Ken before it
   lands, with reporting (W15-K's "Instead of") as the alternative.

## W15.2: Word measured

1. The rows first: themes.md claims STY-060 (the two lists) and moves its Keeping the three in
   agreement table's Word row from LibreOffice to Word's own PDF (W15-A).
2. `apps/worker/src/word-measure.test.ts` (W15-B), as interfaces:
   - `measureInWord(documents): Promise<Map<string, { pdf: Uint8Array; version: string }>>` - the
