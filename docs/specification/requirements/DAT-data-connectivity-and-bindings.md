# DAT - Data connectivity and bindings

> **Status: v1, reviewed.**

## 1. Purpose

Where the numbers come from, and how a number in a document stays connected to the query that
produced it. This area owns connections to source systems, the query definitions that run against
them, the bindings that place a result into content, and the provenance that makes a published
figure defensible.

This is the half of the product that distinguishes it from a very good editor. It is also, with
[IAM](IAM-identity-tenancy-and-access-control.md), one of the two places scope §13 names as the
likeliest source of a serious breach - so, as there, several requirements below say how something
must be enforced rather than only what must be true.

**DAT-064 to DAT-066 give a connection the lifecycle a query definition already had.** DAT-016
protects a query definition from being changed without seeing what it affects; nothing protected the
connection underneath it, which is the thing whose deletion breaks every query at once. Rotation is
the quieter half: credentials change on a schedule somebody else sets, and the failure it can cause
arrives later, in a document, in front of a reader.

**DAT-074 makes every source one the product pulls from, and a file a format rather than a
transport** ([ADR-0035](../../decisions/0035-bindings-hold-stored-results-and-a-publish-never-queries-a-source.md)).
A spreadsheet or a JSON document is read from object storage or over HTTP by the same reader. An
uploaded file is not a source (DAT-N07): an upload is a push, and a push can never be checked for a
revision. S3 was argued in the spike, not run, so its first build is also its first test.

**DAT-075 gives one reason for every failure because two reasons are an oracle.** The spike's
connection test named no address, but the guard's refusals and a failed attempt read differently,
which told an administrator which addresses the guard covers. A refused port, a filtered one, an
unknown host, a guarded address and a wrong password read the same.

**DAT-076 names the two mechanisms "as the end user" can mean.** A delegated token needs a token from
the tenant's own provider to exchange, which a Google-route session and a personal API token do not
have. An asserted identity needs only the principal's name, and holds only under DAT-112 to DAT-114.

**DAT-005 is stated as a capability rather than an intention.** Scope §11 puts it plainly: a token in
a crash report is a breach, not a bug. Testing each path individually is the only version of this
requirement that is worth anything, because the path nobody thought of is the one that leaks.

## 4. Query definitions

A query is an artifact, not a string inside a document. It is named, versioned, reviewed and
permissioned, for the same reason a component is: something dozens of documents depend on cannot be
edited invisibly by whoever last opened one of them.

**DAT-080 and DAT-105 make declaring the columns a second step, the same for every source**
([ADR-0035](../../decisions/0035-bindings-hold-stored-results-and-a-publish-never-queries-a-source.md)).
The connection, then the fetch and its parameters, then a sample run (DAT-014), then the columns.
Only the mapping differs by source - a column name, a pointer, a header or a column letter. A sample
cannot prove a decimal's precision, which is why the author confirms each column rather than the
product guessing. The closed list is what gives a result one canonical form, and so one checksum
(DAT-085), whichever driver or reader delivered it.

**DAT-107 is what makes a checksum move only when the data does.** With no stated order, the spike
flagged unchanged data as moved in 19 of 19 checks against PostgreSQL and 16 of 19 against SQL
Server, because a source may return equal rows in any order.

**DAT-099 and DAT-100 store what the author meant, not the text it compiled to.** A builder whose
stored structure already admits joins, grouping and nested queries can offer them later without
touching a stored query, which versioning (DAT-015) would otherwise make a migration of immutable
data. How much of that structure T2's builder exposes is the design's. Generating the text is also
what keeps an asserted identity safe on a source whose assertion the text could undo (DAT-113).

**DAT-101 to DAT-103 keep SQL written by hand possible and fenced.** No rule over query text is
complete - in the spike a view at the source re-asserted the identity for the text - so the
fallback's protection is the source account's privileges, not parsing. A parameter is still bound
(DAT-081) wherever the text came from.

**DAT-012 is the spike's finding, and it has no sensible default.** A footnote on "row 2" is
meaningless against generated content because the next run can reorder the rows without anybody
editing the document. The anchor must name the data, so the query has to return something that
identifies a row - which makes a query feeding an anchorable table not merely a result set but one
with a primary key.

**DAT-024 is a consequence people do not expect from pass-through.** If two readers of one document
see different numbers because the source shows them different rows, then a _stored_ number is not
"the value" - it is "the value as seen by a particular person at a particular time". Recording whose
view it was is the difference between a defensible figure and an argument.

**DAT-090 and DAT-091 answer DAT-Q03.** Every binding holds a stored result (DAT-083), so a reader
never queries the source, and everybody reading a document sees the same values. The document's
permission decides who reads them; the source's rules decide only who may fetch or accept a new one,
as DAT-025 separates using a connection from reading a document. The cost is that a value one person
could see at the source reaches everyone who can read the document, which is why accepting it warns
at the moment of the act rather than in a setting. The provenance record says whose view it is
(DAT-024, DAT-085).

**DAT-026 is the cache bug that becomes a breach.** A result cached under pass-through carries one
user's access rights inside it, and a cache keyed only on query and parameters will hand it to the
next person who asks. Nothing caches a result in T2 (DAT-052 is T7's); DAT-111 is the bound any
cache built later starts from, because a cached entry outlives the user's permission at the source
for as long as it lives, and nothing tells the product the permission changed.

**DAT-096 to DAT-098 let a result carry pictures without opening a second door.** A bound image is
admitted as an uploaded one is - its own bytes read, decoded whole and bounded - and stored by its
hash, so the stored result holds the hash and its checksum is the same however the source encoded
the image. A picture without a description fails a publish for the same reason an uploaded one does.

**DAT-031 exists because taking the first row is the single most tempting shortcut here.** It works
in testing, where the query returns one row, and it silently reports the wrong number the day the
data grows a second one. A binding that means "the value" must fail when there is more than one.

**DAT-067 is what DAT-029 and DAT-031 needed between them.** "Which value of the result to take" left
the keyed case unstated: a query declaring key columns (DAT-012) can address a row by name, and an
inline binding should be able to say "revenue, for the row keyed EMEA" rather than being restricted
to queries that happen to return one row. Refusing an under-specified binding when it is written
rather than when it runs is the same principle as DAT-020 - the failure belongs to whoever can still
fix it.

## 8. Revising a value by hand

Customers report that a final document always needs a number changed: a figure the source has not
caught up with, a correction agreed in a meeting, a value the author knows to be wrong. A product
that refuses this does not prevent the edit - it moves it into Word, after publication, where nothing
records that it happened.

So revision is specified rather than forbidden, and every requirement here exists to keep it from
costing what section 10 is for. **A revised value is not a data value.** It is a person's value,
standing in a place a query filled, and it must say so everywhere it appears.

| ID          | Requirement                                                                                                                                                                                                                                                                                                                                                                                                  | Tranche    | Status    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- | --------- |
| **DAT-057** | An author must be able to revise a resolved value in place - an inline bound value, or a cell of a bound table - without editing the query definition or the binding                                                                                                                                                                                                                                         | T2         | Specified |
| **DAT-058** | A revision must never replace what the query returned. The binding must retain the resolved value, the value a person entered, who entered it, when, and the reason they gave, and the revision must be audited with what it was and what it became                                                                                                                                                          | Constraint | Specified |
| **DAT-059** | A revised value must be marked as revised by a person wherever it appears - in the editor, in review and in published output - and must never be indistinguishable from a value a query produced                                                                                                                                                                                                             | Constraint | Specified |
| **DAT-060** | A revised binding must still take revisions from its source. Where a source revision arrives (DAT-084), the binding must be flagged, the source value must be shown beside the person's revision, and the author must accept or reject the change deliberately. Accepting a source revision must never silently discard a person's revision, and must never silently keep one over a source that has changed | T2         | Specified |
| **DAT-061** | An outstanding revision must be surfaced to reviewers as something to review, and a lifecycle gate must be able to require that a document has none before it is issued (**COL**, **LIF**)                                                                                                                                                                                                                   | T2         | Specified |
| **DAT-062** | Provenance (DAT-040) for a revised value must record both halves: what the query returned, and the revision that stands in front of it. "Where did this number come from" must be answerable as "a person changed it, and here is what the query said"                                                                                                                                                       | Constraint | Specified |
| **DAT-063** | A revision to a cell of a bound table must be anchored by key (DAT-012), and a revision whose row the query no longer returns must produce a named diagnostic identifying the revision, the key and the query, exactly as DAT-048 does for a footnote                                                                                                                                                        | T2         | Specified |

**DAT-059 is the requirement that makes the rest of this section safe.** A revised number that looks
like a queried number turns section 10 from a guarantee into a claim, because the published lineage
would be describing a value nobody took from a source. Marking it is not a courtesy to the reader, it
is what keeps every other number in the document trustworthy.

**DAT-060 is the case that distinguishes this from typing over a value.** A revision is a statement
about a moment; the source moves afterwards. Silently dropping the revision loses a person's
correction, and silently keeping it over a source that has since agreed, or since disagreed further,
is worse: the document would then be defending a number for a reason nobody remembers. Both outcomes
are available, and neither happens without somebody choosing it.

**DAT-063 borrows the anchoring problem already solved.** A revision to "the EMEA row" cannot be a
revision to row 2, for the same reason a footnote cannot be (DAT-012, DAT-048): the next run reorders
the rows and the correction lands on somebody else's number.

## 9. Stored results and revisions

**Every binding holds a stored result, and nothing a source returns replaces it until a person
accepts it**
([ADR-0035](../../decisions/0035-bindings-hold-stored-results-and-a-publish-never-queries-a-source.md)).
The editor, a preview and a publish read the stored result, so a preview shows what publishing
produces (PUB-006) for data as for text, and everybody reading a document sees the same values. In
this section a **source revision** is a newer result from the source, offered beside the stored one;
it is not section 8's revision, which is a person's value.

**DAT-088 and DAT-089 are where the cost of a live binding went.** A publish that queried its
sources would have needed the publisher's token sealed beside the job, a refresh token held per
session, and a cache whose entries outlive the user's permission at the source; the spike priced
each (case 4). Instead the source is queried while a person is present and acting, and the cost
moves to those acts: creating a document from a template runs every binding while the person waits.

**DAT-084 compares only like with like.** Under end-user identity, a different result for a different
person is a different view, not a source that moved, and flagging it would tell every reader of a
document that its numbers are wrong. They may still fetch their own view and accept it (DAT-091).
The comparison rests on a checksum that moves only when the data does (DAT-085, DAT-107).

**DAT-092 and DAT-093 make a stored result an object of its own now, so that it never has to become
one later.** Turning values embedded in bindings into datasets afterwards would migrate immutable
data. Querying a dataset as a source (DAT-094) is reuse, and waits for T4.

**DAT-070 closes the gap between two kinds of staleness.** DAT-084 watches the data; nothing watched
the query. A binding floating at latest can change what it means - a different column, a different
filter, a different definition of "active customer" - between one publication and the next, with the
source data untouched and no signal anywhere. Provenance records the version afterwards (DAT-085),
which answers the question only once somebody already suspects. How the result of the new version is
offered is the T2 design's, within DAT-082's rule that nothing changes until a person accepts it.

**DAT-072 says where concurrency is decided rather than deciding it again here.** Two authors
accepting source revisions for overlapping bindings is the same problem as two authors editing the same component, and it
now has the same answer in both places.

| **DAT-085** | Every stored result must carry a provenance record: the query definition and its version, the parameters, the connection, the execution identity, the SQL or request that ran, the time, the row count, the dataset version, and a SHA-256 checksum over the result's canonical form, whose version the record names | T2         | Specified             |

**Section 10 is the moat.** Scope §4 names live data lineage as one of the three clauses of the
positioning claim, and this is where it is either true or marketing. The test of it is a single
question asked of a published PDF: _where did this number come from?_ If answering needs anybody to
remember anything, it has failed.

**DAT-085 names the canonical form because a checksum is only as stable as what it is taken over.**
The spike gave one checksum from ten source-and-reader paths in four time zones once every value was
written one way, and a record stored for good (DAT-043) must say which way, so that changing the form
is a new version and never a silent re-hash.

**The split between DAT-044 and DAT-047 is deliberate and was learned in the spike.** Refusing to
render anything makes a broken binding harder to fix, and rendering it silently puts a document with
a missing number in front of a regulator. So resolution reports and continues; publishing refuses.
Since a publish queries no source (DAT-088), the failure is the fetch's (DAT-086), in front of the
person who asked for it, and a binding it left with no stored result is what fails the publish
(DAT-087).

**DAT-108 is the only defence against a truncation the connector cannot see.** In the spike an HTTP
source declaring a `Content-Length` shorter than it sent gave a valid, shorter body with no error, and
a CSV cut at a line break is a valid, shorter file. DAT-045 can be met for such a source only where
something outside the message says how long it is; where nothing does, the gap is the design's to
name, not a requirement to claim closed.

**DAT-068 and DAT-069 answer a question DAT-046 left open.** A binding must never publish a blank in
place of a value it could not resolve - but a query that ran perfectly and found nothing is not that
case, and the two look identical on the page. Which one an empty result is depends on the query, so
the query is what declares it: "no outstanding actions" is a valid and welcome answer, and "no rows
in the revenue table" is a defect.

**DAT-071 fills an ownership vacuum review found, rather than a missing line.** Every limit here was
per query (DAT-050), and per-query limits say nothing about a document with four hundred bindings
created from a template, each resolving at once against one source. The source notices, the tenant next door notices, and
nobody owned the number. Cost reporting stays **ADM**'s; how much may run at once is a property of
querying, which is here.

**DAT-109 and DAT-110 are what a limit has to mean for the source to notice it.** In the spike
neither database driver's own timeout stopped the statement at the source, an HTTP body timeout
counted only idle time, and one value larger than the byte limit cost its whole size in the driver
before any limit acted. Nothing caches a result in T2, so DAT-052 moved to T7 with the
administration; its default, no caching, is what T2 builds.

### What this revision is most exposed on

Section 8 admits a hand-entered value into a document whose selling point is that its numbers come
from somewhere. That is a deliberate trade, and the requirements are built around one line: a revised
value is a person's value and says so everywhere (DAT-059, DAT-N06). If that marking is ever
weakened by a setting, an exception, or a theme that hides it, section 10 stops being a guarantee,
because the published lineage would then be describing numbers nobody took from a source.
